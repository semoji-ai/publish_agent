# 컨텍스트 관리 전략

## 제약 조건

- 실행 모델의 컨텍스트 윈도우는 1M 토큰으로, 원고 한 권을 담을 수 있다. 실제 제약은 창 크기가 아니라 비용과 집중도다
- 한글 1줄 ≈ 30-50 토큰 (평균 40)
- 5000줄 원고 ≈ 200K 토큰 → 한 번에 넣을 수는 있지만 비용이 크고, 관련 없는 원문이 많을수록 판단이 흐려진다
- 긴 세션에서 컨텍스트가 차면 컴팩션이 일어나 이전 원문이 요약으로 바뀐다 → 남겨야 할 결과는 파일에 기록한다

## 핵심 원칙

1. **큰 파일은 나눠 읽는다** — 500줄 이상 파일은 청크 단위로 처리한다. 필요한 부분만 읽어야 비용이 줄고 판단이 선명해진다
2. **읽기 → 요약 → 버리기 → 다음 청크** — 슬라이딩 윈도우 패턴
3. **작업별 토큰 예산 배정** — 스킬마다 읽기/처리/출력 예산 사전 정의
4. **누적 요약만 캐리** — 이전 청크의 원문은 버리고 요약만 유지

## 대용량 파일 처리 패턴

### 패턴 1: 슬라이딩 윈도우 (collect/absorb용)

대용량 원본을 분할 읽기 → 청크별 처리 → 요약 누적

```
전체 파일: 5000줄
  ↓
청크 1: 1-500줄 읽기 → 처리 → 요약 생성 (10줄)
  ↓ (원문 버림, 요약만 유지)
청크 2: 501-1000줄 읽기 → 처리 → 요약 갱신 (15줄)
  ↓
... 반복 ...
  ↓
청크 10: 4501-5000줄 읽기 → 최종 처리
  ↓
결과: 전체 요약 + 주요 인용 + 메타데이터
```

구현:
- Read 도구에 offset/limit 파라미터 사용
- 한 번에 최대 500줄 (약 20K 토큰)
- 각 청크 처리 후 핵심만 추출하여 누적 요약에 추가
- 누적 요약이 100줄(4K 토큰)을 넘으면 요약 자체를 압축

### 패턴 2: 목차 기반 분할 (write/review용)

구조화된 문서의 챕터/섹션 단위로 처리

```
책 원고 (5000줄)
  ↓
목차 추출: 챕터 1 (1-800줄), 챕터 2 (801-1500줄), ...
  ↓
챕터 단위로 처리 (한 번에 1챕터만 컨텍스트에 로드)
  ↓
챕터 간 연결: 이전 챕터 요약만 캐리
```

### 패턴 3: 샘플링 (profile용)

전체를 읽지 않고 대표 샘플만 추출

```
설교문 100편 × 평균 200줄 = 20000줄
  ↓
샘플링: 최근 10편 + 초기 5편 + 무작위 5편 = 20편
  ↓
각 편에서 서론(50줄) + 본론 일부(100줄) + 결론(50줄) 추출
  ↓
총 4000줄 → 8청크로 분할 처리
```

## 스킬별 토큰 예산

| 스킬 | 읽기 예산 | 처리 예산 | 출력 예산 | 총 예산 |
|------|----------|----------|----------|--------|
| collect (파일당) | 20K | 5K | 5K | 30K |
| absorb (항목당) | 30K | 20K | 10K | 60K |
| profile | 40K | 30K | 10K | 80K |
| write (챕터당) | 40K | 40K | 30K | 110K |
| review (챕터당) | 40K | 30K | 20K | 90K |
| sermon | 30K | 20K | 15K | 65K |
| plan (세션당) | 15K | 20K | 5K | 40K |

위 예산은 창 크기 한도가 아니라 비용·집중도를 위한 작업 단위 기준이다. 시스템 프롬프트, 스킬 문서, 대화 이력은 이와 별도로 쌓인다.

## collect 단계 대용량 파일 처리

### 분할 수집 규칙

500줄 이상 파일은 collect 단계에서 이미 분할:

1. 파일 전체 줄 수 확인 (Read로 첫 몇 줄만 읽어 구조 파악)
2. 자연스러운 분할점 탐지:
   - 마크다운 헤딩 (# ## ###)
   - 빈 줄 구분 블록
   - 챕터/절 구분
   - 설교문: 서론/본론/결론 구분
3. 분할점 기준으로 여러 raw entry로 분리 저장
4. 프론트매터에 원본 연결 정보 추가:
   ```yaml
   parent_source_id: src_20260422_001  # 원본 파일 ID
   part: 3                              # 이 파일이 몇 번째 파트인지
   total_parts: 10                      # 전체 파트 수
   part_title: "3장: 은혜의 본질"       # 이 파트의 제목 (있으면)
   ```

### 분할 기준

| 파일 크기 | 처리 방식 |
|----------|----------|
| 500줄 이하 | 그대로 단일 entry |
| 500-2000줄 | 자연 구분점 기준 2-5개 entry로 분할 |
| 2000줄 이상 | 반드시 분할, 각 파트 최대 500줄 |

## absorb 단계 대용량 처리

absorb는 이미 분할된 entry를 처리하므로 개별 entry가 500줄 이하.
하지만 기존 기사가 커지면:

1. 기존 기사 읽을 때 index.md의 summary만 먼저 읽기 (Level 1)
2. 병합 판단에 필요한 chunks/ 만 선택 로드 (Level 2)
3. 전체 기사를 한 번에 읽지 않음

## write 단계 컨텍스트 관리

1. 프로필 로드: style.yaml + theology.yaml = ~2K 토큰 (항상 유지)
2. 현재 챕터 관련 wiki/ 검색: summary 레벨에서 선별 → 필요한 chunks만 로드
3. 이전 챕터: 요약만 유지 (원문 버림)
4. 한 번에 1챕터만 작성
5. 챕터 완료 시: 챕터 요약 생성 → 원문은 파일로 저장 → 컨텍스트에서 제거

## review 단계 컨텍스트 관리

1. 대상 원고가 500줄 이상이면 섹션 단위로 분할 심사
2. 각 섹션: 프로필 + 관련 wiki + 해당 섹션 텍스트만 로드
3. 심사 결과는 파일로 기록 (컨텍스트에 누적하지 않음)

## plan 단계 컨텍스트 관리

1. 프로필 로드: style.yaml + theology.yaml = ~2K 토큰 (상시 유지)
2. plan.yaml: ~1K 토큰 (상시 유지)
3. KB 검색: Level 0~1 위주, 한 번에 10K 토큰 이하
4. interview_log.md: 500줄 초과 시 현재 phase만 로드 (이전 phase는 plan.yaml에 구조화)
5. proposal.md: 갱신 시에만 생성/쓰기, 컨텍스트에 상시 유지하지 않음

## 위험 신호

다음 상황이 감지되면 즉시 분할 처리로 전환:
- 단일 Read 호출에서 1000줄 이상 요청
- 컨텍스트 내 원문 텍스트가 3000줄 이상 누적
- 이전 작업 결과가 참조 불가능해짐 (컴팩션 발생 징후)
