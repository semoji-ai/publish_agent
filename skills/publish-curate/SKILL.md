# Publish Curate — KB 검수 및 정리

위키(KB)의 품질을 두 축으로 검수한다:
- **오염 검수** — 저자 프로필 기준 이질적 항목 감지 및 제거
- **인덱싱 검수** — 위키링크 밀도·역링크 정합성·기사 충실도·인덱스 완전성 점검

모든 삭제·수정은 스냅샷 기반으로 복구 가능하다.

## 트리거 조건

```
- "/publish-curate"
- "위키 정리해줘"
- "잘못된 자료 있는지 확인해줘"
- "오염된 자료 찾아줘"
- "이 배치 롤백해줘"
- "배치 롤백"
- "KB 정리"
- "인덱싱 검수해줘"
- "위키링크 검사해줘"
- "고아 기사 찾아줘"
- "흡수 퀄리티 확인해줘"
```

## 사전 조건

- config.yaml 존재 (publish-setup 완료)
- wiki/ 디렉토리에 기사 존재
- authors/{author_id}/ 프로필 파일 존재 (오염 검수 시 필수, 인덱싱 검수 시 권장)

---

## WHEN TRIGGERED - EXECUTE IMMEDIATELY

### Step 1: 검수 모드 선택

사용자에게 검수 모드를 확인한다:

```
검수 모드를 선택하세요:
  1. 오염 검수 — 신학적 이질성, 출처 혼용, 카테고리 오분류 감지
  2. 인덱싱 검수 — 위키링크 밀도, 역링크 정합성, 기사 충실도, 인덱스 완전성
  3. 전체 검수 — 1+2 통합 실행
```

사용자 의도가 명확하면 질문 없이 진행:
- "위키링크 검사해줘", "인덱싱 검수" → 모드 2
- "오염된 자료 찾아줘", "배치 롤백" → 모드 1
- "전체 검수", "위키 정리해줘" → 모드 3

**모드 1 → Step 2로 진행 (오염 검수)**
**모드 2 → Step 10으로 진행 (인덱싱 검수)**
**모드 3 → Step 2 완료 후 Step 10으로 연속 진행**

# 오염 검수 (모드 1)

### Step 2: 검수 범위 확인

사용자에게 검수 범위를 확인한다:

```
1. 전체 — wiki/ 모든 기사 대상
2. 특정 배치 — batch_id 지정 (예: batch_20260421)
3. 특정 출처 — source_id 지정 (예: src_20260421_003)
```

범위가 명확하지 않으면 질문한다. 단, 사용자가 "이 배치 롤백해줘"처럼 의도가 명확하면 추가 질문 없이 진행한다.

**batch_id / source_id 확인 방법:**
- `wiki/_absorb_log.json` 의 `batches` 배열에서 확인
- raw/entries/ 프론트매터의 `batch_id`, `source_id` 필드에서 확인

### Step 3: 자동 스냅샷 생성

검수 실행 전 반드시 스냅샷을 생성한다. 롤백 기준점이 된다.

생성 위치: `snapshots/{YYYY-MM-DDTHHMMSS}/`

생성 파일:
1. `manifest.json`
   ```json
   {
     "created_at": "{ISO 8601 타임스탬프}",
     "trigger": "pre_curate",
     "description": "curate 실행 전 자동 스냅샷",
     "article_count": {현재 wiki/ 기사 수}
   }
   ```
2. `wiki/_index.md` 사본
3. `wiki/_backlinks.json` 사본

### Step 4: 저자 프로필 로드

`config.yaml`에서 `author.id`를 읽어 `authors/{author_id}/` 하위 4개 파일을 로드한다:

- `theology.yaml` — 신학적 입장
- `style.yaml` — 문체
- `sermon_pattern.yaml` — 설교 구조 패턴
- `vocabulary.md` — 어휘 패턴

프로필이 비어 있으면 (publish-profile 미실행 상태) 경고를 표시하고 계속 진행한다:
```
저자 프로필이 비어 있습니다. /publish-profile을 먼저 실행하면 더 정확한 이질성 감지가 가능합니다.
현재 상태로 진행하려면 엔터를 누르세요.
```

### Step 5: 대상 항목 스캔 및 이질성 감지

검수 범위에 해당하는 기사/항목을 스캔한다. `deleted: true`인 항목은 건너뛴다.

**스캔 대상:**
- 범위 = 전체: `wiki/` 모든 카테고리의 `index.md`
- 범위 = 특정 배치: 해당 `batch_id`가 `sources` 필드에 포함된 기사
- 범위 = 특정 출처: 해당 `source_id`가 `sources` 필드에 포함된 기사

**이질성 감지 기준 (저자 프로필 대비):**

| 유형 | 감지 조건 | 심각도 |
|------|-----------|--------|
| 신학적 이질성 | 기사 내용이 theology.yaml의 저자 입장과 상충 | HIGH |
| 문체 불일치 | 저자 1차 자료(primary)인데 style.yaml과 현저히 다른 어투 | MEDIUM |
| 출처 혼용 | reference 자료가 저자의 주장으로 표현됨 | HIGH |
| 카테고리 오분류 | 설교가 concepts/에 들어간 경우 등 | LOW |
| 중복 의심 | 동일 내용이 복수 기사에 분산 | LOW |

각 항목에 대해 이질성 여부와 유형을 판단한다. 이질성이 없는 항목은 리포트에서 제외한다.

### Step 6: 플래그 리포트 출력

이질성이 감지된 항목을 표 형태로 사용자에게 제시한다:

```
## 오염 검수 결과: {N}개 항목 플래그됨

| 기사명 | 이질성 유형 | 출처(source_id) | 배치(batch_id) | 심각도 |
|--------|------------|----------------|----------------|--------|
| 구원론  | 신학적 이질성: 저자 입장(개혁주의)과 상충하는 아르미니우스적 서술 | src_20260421_007 | batch_20260421 | HIGH |
| ...    | ...        | ...            | ...            | ...    |

이질성 없음: {M}개 기사 (스캔 완료)
```

플래그된 항목이 없으면:
```
오염 검수 완료. 이질성이 감지된 항목이 없습니다. 위키 상태가 양호합니다.
```
→ Step 8로 건너뛴다.

### Step 7: 사용자 선택 및 실행

사용자에게 처리 방법을 선택하게 한다:

```
각 항목에 대해 처리 방법을 선택하세요:
  [S] Soft delete — 해당 기사를 삭제 표시 (복구 가능)
  [R] 배치 롤백 — 해당 배치 전체를 롤백
  [I] 무시 — 이 항목은 그대로 유지

항목별로 선택하거나, 전체 일괄 처리를 선택할 수 있습니다.
```

**7a: Soft Delete 실행**

선택된 기사의 `index.md` 프론트매터에 `deleted: true`를 추가한다:

```yaml
---
title: 구원론
deleted: true
# ...나머지 필드 유지
---
```

- 파일 자체는 삭제하지 않는다 (복구 가능)
- 이후 `_index.md`에서 해당 항목을 제외한다
- 해당 기사의 `chunks/`는 유지한다

**7b: 배치 롤백 실행**

1. 사용자가 지정한 `batch_id`에 해당하는 스냅샷을 `snapshots/`에서 찾는다
   - 해당 배치의 absorb 직전 스냅샷 (`manifest.json`의 `batch_id` 확인)
   - 스냅샷이 없으면 경고: "해당 배치의 스냅샷이 없습니다. 개별 soft delete를 사용해주세요."
2. 스냅샷의 `wiki/_index.md`와 `wiki/_backlinks.json`을 현재 파일에 복원한다
3. 해당 배치에서 생성/수정된 기사를 특정하여:
   - 해당 배치에서 **신규 생성**된 기사: `deleted: true` 처리
   - 해당 배치에서 **수정**된 기사: 수정 전 상태 복원 (스냅샷 내 사본 기준)
4. 해당 배치의 raw/entries/ 항목을 `absorbed: false`로 되돌린다

**7c: 무시**

아무 처리도 하지 않고 다음 항목으로 넘어간다. 로그에 "사용자가 무시 선택"을 기록한다.

### Step 8: _index.md 및 _backlinks.json 재구축

처리가 완료된 후 인덱스를 재구축한다.

**_index.md 재구축:**
- `wiki/` 전체 기사 스캔
- `deleted: true`인 기사 제외
- 각 기사의 `title`과 `summary` 필드 추출
- 카테고리별 `_index.md` 재생성
- 루트 `wiki/_index.md` 재생성

**_backlinks.json 재구축:**
- `deleted: true`가 아닌 모든 기사의 `[[위키링크]]` 추출
- 역링크 맵 재구성 후 `wiki/_backlinks.json` 갱신

### Step 9: 오염 검수 완료 리포트

```
오염 검수 완료.

처리 결과:
  Soft delete: {N}개 기사
  배치 롤백: {batch_id} ({M}개 기사 영향)
  무시: {K}개 항목

인덱스 재구축 완료:
  _index.md 갱신
  _backlinks.json 갱신

스냅샷: snapshots/{timestamp}/
복구가 필요하면: "이전 상태로 복구해줘" 또는 해당 스냅샷 경로를 알려주세요.
```

**모드 3(전체 검수)이면 Step 10으로 계속 진행. 그 외에는 종료.**

# 인덱싱 검수 (모드 2)

### Step 10: 볼트 전체 스캔

wiki/ 전체를 스캔하여 기초 통계를 수집한다. `deleted: true` 기사는 제외.

**수집 항목:**
- 총 기사 수 (카테고리별)
- 기사당 본문 줄 수 (index.md + chunks/ 합산)
- 기사당 위키링크 수 (`[[...]]` 패턴 카운트)
- 기사당 역링크 수 (`_backlinks.json` 기준)
- 기사당 sources 수
- summary 필드 유무 및 길이
- related 필드 항목 수

스캔 시 **컨텍스트 관리 원칙 준수**: 각 기사의 프론트매터와 본문 첫 50줄만 읽어 통계 추출. 전문 읽기는 Step 12(충실도 검사)에서 필요 시에만 수행.

스캔 완료 후 기초 통계를 사용자에게 보고:

```
## 볼트 기초 통계

총 기사: {N}개
카테고리별: concepts {n}개 / sermons {n}개 / passages {n}개 / ...

기사당 평균:
  위키링크: {avg}개 (최소 {min} / 최대 {max})
  역링크: {avg}개 (최소 {min} / 최대 {max})
  본문 줄 수: {avg}줄 (최소 {min} / 최대 {max})
```

### Step 11: 위키링크 밀도 검사

#### 11a: 기사별 위키링크 밀도 측정

각 기사의 본문(index.md + chunks/)에서 `[[...]]` 패턴을 추출하고, 기사 분량 대비 링크 밀도를 계산한다.

**밀도 기준:**

| 기사 분량 | 최소 위키링크 수 | 판정 |
|-----------|-----------------|------|
| 50줄 미만 | 2개 | SPARSE 이하 시 플래그 |
| 50-150줄 | 4개 | SPARSE 이하 시 플래그 |
| 150줄 이상 | 6개 | SPARSE 이하 시 플래그 |

추가 플래그 조건:
- **고아 기사(orphan)**: 위키링크도 0개이고, 역링크도 0개인 기사 → 다른 기사와 완전 단절
- **편향 링크**: 위키링크는 많지만 역링크가 0인 기사 → 다른 기사에서 참조하지 않음
- **관련 기사 미연결**: `related` 필드가 비어있는 기사

#### 11b: 끊어진 위키링크 검출

본문에 `[[기사명]]`이 있지만 해당 기사가 wiki/에 존재하지 않는 경우를 탐지한다.

- 끊어진 링크(broken link): 기사 디렉토리 자체가 없음
- 삭제된 기사 링크: 대상 기사가 `deleted: true` 상태

#### 11c: 역링크 정합성 검증

`_backlinks.json`과 실제 위키링크를 대조한다:

- `_backlinks.json`에 있지만 실제 링크가 없는 항목 (팬텀 역링크)
- 실제 링크가 있지만 `_backlinks.json`에 누락된 항목 (누락 역링크)

**출력:**

```
## 위키링크 검사 결과

### SPARSE 기사 ({N}개)
| 기사명 | 분량 | 위키링크 수 | 최소 기준 | 역링크 수 |
|--------|------|-----------|----------|----------|
| 이사야_03장 | 85줄 | 1개 | 4개 | 2개 |
| ... | | | | |

### 고아 기사 ({N}개) — 위키링크 0, 역링크 0
- {기사명} ({분량}줄)

### 끊어진 위키링크 ({N}개)
| 출처 기사 | 대상 [[링크]] | 상태 |
|-----------|-------------|------|
| 구원론 | [[성령론]] | 기사 없음 |

### 역링크 불일치 ({N}개)
- 팬텀: {n}건 (backlinks.json에만 존재)
- 누락: {n}건 (실제 링크만 존재)
```

### Step 12: 기사 충실도 검사

raw entry 대비 위키 기사가 원본 내용을 충분히 반영하는지 검사한다.

**검사 방법:**

각 기사의 `sources` 필드에서 source_id를 추출하고, 해당 `raw/entries/` 파일을 찾는다.

1. **분량 비율 검사**: raw entry 본문 줄 수 대비 위키 기사(index.md + chunks/) 줄 수 비율 계산
   - 비율 < 0.3 (원본의 30% 미만) → `THIN` 플래그
   - 비율 0.3-0.7 → 정상 범위 (요약이 적절)
   - 비율 > 1.5 → `EXPANDED` (정상 — 여러 출처 통합)

2. **핵심 키워드 커버율**: raw entry에서 고빈도 명사(상위 10개)를 추출하고, 위키 기사에 해당 키워드가 포함되어 있는지 확인
   - 커버율 < 50% → `KEYWORD_MISSING` 플래그
   - 커버율 50-80% → 정상
   - 커버율 > 80% → 양호

**출력:**

```
## 기사 충실도 검사 결과

### THIN 기사 ({N}개) — 원본 대비 과도하게 축약됨
| 기사명 | raw entry 줄수 | 위키 기사 줄수 | 비율 | 키워드 커버율 |
|--------|---------------|-------------|------|-------------|
| 이사야_05장_강해 | 320줄 | 45줄 | 14% | 40% |

### KEYWORD_MISSING ({N}개) — 핵심 키워드 누락
| 기사명 | 누락 키워드 | 커버율 |
|--------|-----------|--------|
| 이사야_05장_강해 | 화, 포도원, 심판 | 35% |
```

### Step 13: summary 품질 검사

각 기사의 `summary` 프론트매터 필드를 검사한다.

**검사 기준:**

| 항목 | 기준 | 플래그 |
|------|------|--------|
| summary 부재 | summary 필드가 없거나 빈 문자열 | `NO_SUMMARY` |
| summary 과소 | 1문장 미만 (30자 미만) | `SHORT_SUMMARY` |
| summary 불일치 | summary 내용이 본문 첫 섹션과 주제가 다름 | `MISMATCH_SUMMARY` |
| 요약 블록 누락 | `> **요약:**` 블록이 본문에 없음 | `NO_SUMMARY_BLOCK` |

**출력:**

```
## summary 품질 검사 결과

| 기사명 | 플래그 | 현재 summary |
|--------|--------|-------------|
| 칭의 | NO_SUMMARY | (없음) |
| 은혜 | SHORT_SUMMARY | "은혜에 관한 기사" |
```

### Step 14: 인덱스 정합성 검사

_index.md 파일들이 실제 위키 기사 상태를 정확히 반영하는지 확인한다.

**검사 항목:**

1. **누락 기사**: wiki/에 존재하지만 _index.md에 등재되지 않은 기사
2. **유령 항목**: _index.md에 등재되어 있지만 wiki/에 존재하지 않는(또는 deleted: true인) 기사
3. **카테고리 불일치**: 기사의 `type` 필드와 실제 디렉토리 카테고리가 다른 경우
4. **chunk_count 불일치**: 프론트매터 `chunk_count`와 실제 chunks/ 파일 수가 다른 경우

**출력:**

```
## 인덱스 정합성 검사 결과

누락 기사 ({N}개): _index.md에 미등재
- wiki/concepts/성화/ (type: concept)

유령 항목 ({N}개): _index.md에만 존재
- [[예정론]] (concepts/_index.md에 기재)

카테고리 불일치 ({N}개):
- wiki/concepts/이사야/ → type: passage (concepts/ 아닌 passages/에 있어야 함)

chunk_count 불일치 ({N}개):
- 구원론: chunk_count=2 but chunks/ has 3 files
```

### Step 15: 인덱싱 검수 종합 리포트

모든 검사 결과를 종합하여 KB 건강도 점수와 함께 보고한다.

```
## 인덱싱 검수 종합 리포트

KB 건강도: {점수}/100

### 점수 산출 근거
- 위키링크 밀도: {점수}/25 (SPARSE {n}개, 고아 {n}개)
- 역링크 정합성: {점수}/25 (불일치 {n}건)
- 기사 충실도: {점수}/25 (THIN {n}개, KEYWORD_MISSING {n}개)
- 인덱스 정합성: {점수}/25 (누락 {n}개, 유령 {n}개)

### 우선 수정 대상
1. [위키링크] SPARSE 기사 {N}개 — 위키링크 자동 보강 권장
2. [충실도] THIN 기사 {N}개 — 원본 재흡수 또는 보강 필요
3. [인덱스] 누락/유령 {N}건 — 인덱스 재구축 필요
4. [summary] 부재/과소 {N}건 — summary 자동 생성 권장
```

### Step 16: 자동 보강 실행

사용자에게 자동 보강 범위를 제안한다:

```
자동 보강할 항목을 선택하세요:

  [L] 위키링크 보강 — SPARSE 기사에 위키링크 자동 추가
  [I] 인덱스 재구축 — _index.md, _backlinks.json 전면 재구축
  [S] summary 보강 — NO_SUMMARY, SHORT_SUMMARY 기사에 summary 자동 생성
  [T] THIN 기사 재흡수 — raw entry 기반으로 위키 기사 내용 보강
  [A] 전체 자동 보강 — L+I+S 실행 (T는 수동 확인 필요)
  [N] 보강하지 않음 — 리포트만 확인
```

#### 16a: 위키링크 보강 [L]

SPARSE 플래그된 각 기사에 대해:

1. 기사 본문에서 다른 위키 기사 제목과 일치하는 키워드를 탐색
2. 일치하는 키워드를 `[[위키링크]]`로 변환
3. `related` 필드에도 해당 기사 추가
4. 변경 내역을 사용자에게 보고 (기사당 추가된 링크 수)

**위키링크 추가 규칙:**
- 기사 본문에 이미 존재하는 키워드만 링크 (새 텍스트를 삽입하지 않음)
- 동일 기사 내에서 같은 링크는 첫 등장만 변환
- 자기 참조 금지
- 대상 기사가 wiki/에 실제 존재하는 경우만 링크

#### 16b: 인덱스 재구축 [I]

`shared/references/absorb-rules.md` 7장의 재구축 절차를 그대로 실행:
- 카테고리별 `_index.md` 재생성
- 루트 `wiki/_index.md` 재생성
- `_backlinks.json` 전면 재구축

#### 16c: summary 보강 [S]

NO_SUMMARY, SHORT_SUMMARY 플래그된 기사에 대해:
1. 기사 본문(index.md 첫 100줄)을 읽는다
2. 2-3문장 summary를 생성한다 (wiki-article-format.md의 summary 작성 원칙 준수)
3. 프론트매터 `summary` 필드 업데이트
4. 본문에 `> **요약:**` 블록이 없으면 추가

#### 16d: THIN 기사 재흡수 [T]

THIN 플래그된 기사에 대해 **사용자 확인 후** 개별 처리:

```
THIN 기사: {기사명}
  현재: {위키 줄수}줄 (원본 {raw 줄수}줄의 {비율}%)
  raw entry: {source_id}

  [R] 재흡수 — raw entry 기반으로 기사 내용 보강
  [S] 건너뜀
```

재흡수 실행 시:
1. 해당 raw entry 전문 읽기
2. `publish-absorb/references/absorb-prompt.md`의 기사 작성 지침에 따라 기사 본문 재작성
3. 기존 기사 내용과 병합 (중복 없이)
4. chunks/ 필요 시 분리

### Step 17: 인덱싱 검수 완료 리포트

```
인덱싱 검수 완료.

보강 결과:
  위키링크 추가: {N}개 기사, 총 {M}개 링크 추가
  인덱스 재구축: _index.md {n}개 갱신, _backlinks.json 갱신
  summary 보강: {N}개 기사
  THIN 기사 재흡수: {N}개 기사

KB 건강도: {이전 점수}/100 → {현재 점수}/100

스냅샷: snapshots/{timestamp}/
```

## 버전 관리 및 복구 안내

- **Soft delete:** `deleted: true` 플래그만 추가, 파일은 보존됨. 복구 시 `deleted: false`로 변경하고 인덱스 재구축.
- **배치 롤백:** `snapshots/{timestamp}/`의 인덱스와 백링크를 복원. 원본 raw/entries/ 항목은 보존됨.
- **스냅샷 자동 생성 시점:** curate 실행 전, absorb 실행 전
- **수동 복구:** 사용자가 "이전으로 되돌려줘"라고 하면 가장 최근 스냅샷으로 복원 제안

## KB 건강도 점수 산출 기준

### 위키링크 밀도 (25점)

```
감점 = (SPARSE 기사 수 / 전체 기사 수) × 25
고아 기사 1개당 추가 감점 2점
점수 = max(0, 25 - 감점)
```

### 역링크 정합성 (25점)

```
불일치율 = (팬텀 + 누락) / 전체 역링크 항목 수
점수 = max(0, 25 × (1 - 불일치율))
끊어진 링크 1개당 추가 감점 1점
```

### 기사 충실도 (25점)

```
감점 = (THIN 기사 수 / source 연결 기사 수) × 20
KEYWORD_MISSING 1건당 추가 감점 1점
점수 = max(0, 25 - 감점)
```

### 인덱스 정합성 (25점)

```
오류 수 = 누락 기사 + 유령 항목 + 카테고리 불일치 + chunk_count 불일치
감점 = min(25, 오류 수 × 2)
점수 = max(0, 25 - 감점)
```
