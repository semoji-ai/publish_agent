# 흡수 프롬프트 템플릿

이 파일은 `/publish-absorb` 스킬이 항목을 위키 기사로 변환할 때 단계별로 적용하는 프롬프트 템플릿을 정의한다. 각 섹션은 흡수 워크플로우의 특정 단계에 대응한다.

---

## 1. 항목 분석 프롬프트

**사용 시점:** Step 2a — 각 raw entry를 처음 읽을 때

**목적:** "이 자료가 무엇인가(파일 유형/출처)"가 아닌, "이 자료가 **무엇을 의미하는가**"를 파악한다.

---

### [항목 분석]

다음 원문을 읽고 아래 질문에 답하라.

**원문:**
```
{raw entry 전체 내용}
```

**분석 질문:**

**1. 핵심 주제는 무엇인가?**
이 항목이 실질적으로 다루는 중심 내용을 1-2문장으로 기술하라. 파일 제목이 아닌, 내용의 본질적 의미를 파악하라.
- 설교문이라면: 어떤 신학적 주장 또는 본문 해석을 담고 있는가?
- 저서 챕터라면: 어떤 개념이나 논증을 전개하는가?
- 신학 논문이라면: 저자의 어떤 입장을 지지하거나 비판하는가?

**2. 카테고리 결정**
아래 기준에 따라 이 항목이 속할 위키 카테고리를 하나 선택하라:

| 카테고리 | 해당 항목 유형 |
|----------|---------------|
| `people` | 신학자, 성경 인물, 역사적 인물에 관한 항목 |
| `concepts` | 신학적 개념 (구원론, 은혜, 언약, 칭의, 성화 등) |
| `sermons` | 저자 본인의 설교 또는 설교 시리즈 |
| `books` | 저자 본인의 저서 또는 타 저자의 저서 |
| `passages` | 특정 성경 본문 또는 단락 해석 |
| `references` | 신학 논문, 주석, 성경 사전, 기타 학술 참고자료 |

항목이 여러 카테고리에 걸쳐 있으면 **주된** 성격으로 결정한다.

**3. 기사 제목 후보**
위키에서 사용할 기사 제목을 1-3개 제안하라. 기준:
- 간결하고 명확 (1-4단어)
- 한국 신학 위키 용례에 맞는 용어 사용
- 기존 기사 제목과 충돌 가능성 낮은 것 우선

**4. 핵심 키워드 및 위키링크 후보**
이 항목에서 추출할 수 있는 핵심 개념/인물/본문을 목록으로 나열하라. 이 키워드들이 기존 기사와의 매칭 및 위키링크 생성에 사용된다.

**5. 저자 고유성**
이 항목이 저자(1차 자료: primary)의 것인가, 참고 자료(2차 자료: reference)인가?
- primary: 저자의 독자적 입장, 주장, 해석이 담겨 있음
- reference: 타인의 저작으로 저자의 연구에 참고된 자료

---

## 2. 카테고리 결정 상세 기준

**사용 시점:** Step 2a — 분석 결과에서 카테고리가 모호할 때 추가 판단

---

### [카테고리 결정 기준 상세]

모호한 경우 다음 기준을 순서대로 적용한다:

**people vs concepts:**
- 주제가 특정 인물에 관한 것이면 → `people`
- 그 인물의 신학적 주장이 중심이고 인물 자체가 배경이면 → `concepts`
- 예: "칼빈의 예정론" → 내용이 예정론 개념이라면 `concepts`, 칼빈의 생애/사상이라면 `people`

**sermons vs passages:**
- 저자가 특정 성경 본문으로 설교한 내용이면 → `sermons` (설교 자체가 기사)
- 성경 본문 자체의 해석/주해가 중심이면 → `passages`
- 같은 본문이라도 설교집 수록 설교는 `sermons`, 주석 내용은 `passages`

**books vs references:**
- 저자 본인의 저서 → `books`
- 타 저자의 저서로 참고자료로 사용 → `references`
- 논문, 주석서, 성경 사전 → `references`

**concepts 생성 기준:**
- 항목에서 반복 등장하는 신학 용어가 있고, 저자의 고유한 정의나 입장이 포함되어 있을 때
- 이미 `wiki/concepts/`에 해당 기사가 없을 때
- 예: "은혜", "언약", "구원", "칭의", "성화", "종말", "교회", "성령" 등

## 3. 신규 기사 작성 프롬프트

**사용 시점:** Step 2c — 매칭된 기존 기사가 없어 새 기사를 생성할 때

---

### [신규 기사 작성]

분석 결과를 바탕으로 다음 형식에 따라 위키 기사를 작성하라.

**카테고리:** {분석 결과 카테고리}
**기사 제목:** {선택된 기사 제목}
**출처 항목:** {source_id}
**자료 유형:** {primary | reference}

**작성 규칙:**

1. **어조 — 백과사전식, 중립적**
   - 1차 자료(저자 본인): "저자는 ~라고 주장한다", "저자의 입장에 따르면 ~이다", "저자는 ~를 강조한다"
   - 2차 자료(참고문헌): "~에 따르면", "~는 ~라고 설명한다", "~에서 ~를 논증하고 있다"
   - 개인 감정, 평가, 추천 표현 금지

2. **구조 — 필수 섹션**
   - 상단 요약 블록: `> **요약:** {핵심을 2-3문장으로}` — LLM 검색 시 이 요약이 먼저 로드됨
   - 본문: 주제별 섹션으로 구성 (## 헤딩 사용)
   - 관련 항목: `## 관련 항목` 섹션에 위키링크 목록
   - (설교/저서 기사) 관련 설교/저서: `## 관련 설교` 또는 `## 관련 저서` 섹션

3. **위키링크 — 관련 개념마다 적용**
   - 언급된 신학 개념, 인물, 성경 본문, 저서마다 `[[기사명]]` 적용
   - 같은 기사명은 첫 등장에만 링크
   - 아직 존재하지 않는 기사도 링크 가능 (향후 생성될 기사를 위해)

4. **길이 기준**
   - 최소: 15줄 이상 (그 미만이면 기존 기사에 섹션으로 통합)
   - 권장: 30-100줄 (충분한 내용 + 적절한 밀도)
   - 최대: 200줄 (초과 시 chunks/ 분리 또는 하위 기사 독립)

5. **프론트매터 작성**
   ```yaml
   ---
   title: {기사 제목}
   type: {person|concept|sermon|book|passage|reference}
   created: {오늘 날짜 YYYY-MM-DD}
   updated: {오늘 날짜 YYYY-MM-DD}
   summary: "{요약 2-3문장 — 검색용이므로 핵심 정보 우선}"
   related:
     - "[[관련기사1]]"
     - "[[관련기사2]]"
   sources:
     - {source_id}
   tags:
     - {관련 태그}
   chunk_count: 0
   ---
   ```

**summary 필드 작성 기준:**
- 1차 자료: "저자의 {주제}에 대한 입장: {핵심 주장}. {추가 맥락}."
- 2차 자료: "{저자명}의 {저작물}에서 {핵심 내용}을 다룬다. {위키와의 관련성}."
- LLM이 `_index.md`를 스캔할 때 이 한 줄로 관련성을 판단하므로, 검색 키워드를 자연스럽게 포함하라.

## 4. 기존 기사 병합 프롬프트

**사용 시점:** Step 2c — 매칭된 기존 기사에 새 내용을 통합할 때

---

### [기존 기사 병합]

기존 기사에 새 항목의 내용을 통합하라.

**기존 기사:**
```
{wiki/{category}/{기사명}/index.md 전체 내용}
```

**기존 청크 (있는 경우):**
```
{chunks/001.md, 002.md 등}
```

**새로 흡수할 항목:**
```
{raw entry 내용}
```

**병합 규칙:**

1. **기존 기사 완전 재독** — 기존 내용을 먼저 완전히 파악한 후 병합을 시작한다. 섣불리 추가하지 않는다.

2. **중복 방지** — 이미 기술된 내용은 다시 쓰지 않는다. 새 항목이 기존 내용을 더 정확하게 기술하면 기존 내용을 교체한다.

3. **자연스러운 통합** — 새 내용을 기계적으로 뒤에 붙이지 않는다. 적절한 섹션을 찾아 통합하거나, 새 섹션을 추가하되 기사 전체의 흐름이 유지되도록 한다.

4. **출처 추가** — 프론트매터의 `sources` 배열에 새 `source_id`를 추가한다.

5. **날짜 갱신** — 프론트매터의 `updated` 필드를 오늘 날짜로 갱신한다.

6. **요약 재작성** — 새 내용이 통합된 후 `summary` 필드와 상단 요약 블록을 기사 전체를 반영하여 재작성한다.

7. **200줄 초과 체크** — 병합 후 기사가 200줄을 초과하면:
   - 독립 가능한 하위 주제가 있는지 검토
   - 있으면: 해당 섹션을 별도 기사로 분리 후 위키링크로 연결
   - 없으면: chunks/ 파일로 분리하고 `chunk_count` 갱신

**병합 후 검토 체크리스트:**
- [ ] 기존 내용이 손실되지 않았는가?
- [ ] 새 내용이 기사 흐름에 자연스럽게 통합되었는가?
- [ ] summary가 갱신된 전체 내용을 반영하는가?
- [ ] 위키링크가 새 내용에서도 적용되었는가?
- [ ] sources에 새 source_id가 추가되었는가?

## 5. 청크 분리 기준 및 프롬프트

**사용 시점:** Step 2c — 기사 본문이 100줄 이상일 때

---

### [청크 분리]

기사 본문이 길어지면 주제별로 `chunks/` 파일로 분리하여 LLM이 필요한 부분만 로드할 수 있게 한다.

**분리 기준:**
- 기사 `index.md` 본문(프론트매터 제외)이 **100줄 이상**이면 분리 검토
- **200줄 이상**이면 반드시 분리

**분리 원칙:**

1. **주제별 분리** — 각 청크는 하나의 완결된 소주제를 다룬다. 임의로 줄 수로 자르지 않는다.

2. **자체 완결성** — 각 청크는 단독으로 읽어도 의미를 파악할 수 있어야 한다. 청크 상단에 간단한 맥락 문장을 포함한다.

3. **index.md 유지** — `index.md`는 요약 + 섹션 개요만 유지한다. 상세 내용은 청크로 이동.

4. **파일명 규칙** — `chunks/001.md`, `chunks/002.md` (순서 번호, 3자리)

5. **chunk_count 갱신** — `index.md` 프론트매터의 `chunk_count` 필드를 실제 청크 수로 갱신

**index.md 청크 참조 형식:**
```markdown
## {섹션 제목}

> 상세 내용: [[chunks/001]]

{섹션의 핵심 요점 2-3줄 — 청크 로드 전 판단용}
```

**청크 파일 형식 (chunks/001.md):**
```markdown
---
chunk_of: {기사명}
chunk_index: 1
title: "{이 청크의 소주제}"
---

# {소주제 제목}

> **맥락:** 이 청크는 [[{기사명}]] 기사의 일부로, {소주제}를 다룬다.

{상세 내용}
```

## 6. 품질 규칙 (Quality Rules)

**사용 시점:** 기사 작성/병합 후 최종 검토 단계에서 적용

---

### [품질 검토 체크리스트]

작성 또는 병합된 기사가 다음 기준을 충족하는지 확인한다:

**금지 표현:**
- 이모지 사용 금지 (예: ✨, 📖, 🔥 등)
- 대시(-) 남용 금지 — 문장 부호로만 사용, 장식적 구분선으로 남용 금지
- "전설적", "진정으로", "흥미롭게도", "놀랍게도" 등 과장 표현 금지
- "매우", "정말", "굉장히" 등 강도 부사 남용 금지

**문장 작성:**
- 짧고 명확한 문장 선호 — 한 문장에 하나의 개념
- 수동태보다 능동태 선호
- 중문보다 단문 + 연결 선호

**귀속 표기 우선 (Attribution-first):**
- 주장이나 관점을 기술할 때 반드시 출처를 먼저 명시한다
- 올바른 예: "저자는 은혜의 무조건성을 강조하며, 인간의 공로가 구원에 개입할 여지가 없다고 주장한다."
- 잘못된 예: "은혜는 무조건적이며 인간의 공로는 구원과 무관하다." (출처 불명확)

**내용 정확성:**
- 원문에 없는 내용을 추론하여 추가하지 않는다
- 불확실한 내용은 기술하지 않거나 "~로 추정된다" 등 단서 표현 사용
- 신학적 입장은 저자의 실제 입장을 기록하고, LLM의 판단을 투영하지 않는다

**위키링크 품질:**
- 실제로 관련된 개념에만 링크 — 단순 언급에 모두 링크하지 않는다
- 기사 제목과 정확히 일치하는 이름으로 링크 (대소문자, 띄어쓰기 포함)
- 존재하지 않는 기사 링크는 향후 생성될 것으로 기대되는 중요 개념에만 허용

**요약(summary) 품질:**
- 검색 키워드를 자연스럽게 포함
- 기사 전체의 핵심을 2-3문장으로 압축
- 과도한 상세화 금지 — 요약은 탐색 판단용이지 기사 전체를 대체하지 않는다
